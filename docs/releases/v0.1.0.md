# OpenPool v0.1.0 release notes

> Status: release draft. Do not create the final `v0.1.0` tag until every required item in the release checklist is complete.

OpenPool `v0.1.0` is the first stable project release of the self-hosted, Cloudflare-native object storage control plane. It combines storage accounts into a logical pool while keeping object bytes on the direct client-to-provider data path.

## Highlights

- Unified logical buckets across Cloudflare R2, Backblaze B2, and S3-compatible storage
- Capacity-aware placement and explicit storage account, shard, object, and upload state machines
- Direct signed upload and download transfers that never proxy object bytes through the Worker
- Encrypted provider credentials, scoped API keys, secure administrator sessions, authentication rate limiting, and deployment readiness checks
- Upload recovery, scheduled stale-attempt cleanup, account drain, and client-mediated cross-provider shard migration
- Transactional audit outbox and searchable audit history
- English and Simplified Chinese administration console
- TypeScript SDK and object/migration CLIs for self-hosted workflows

## Verified environments

- Full repository verification through Oxlint, TypeScript, Vitest, Workers Vitest, and production builds
- Isolated Cloudflare staging Worker, Static Assets, D1, Secrets, rate limit bindings, and scheduled maintenance
- Real Cloudflare R2 and Backblaze B2 browser-direct upload, download, delete, retry, and migration workflows
- R2 and B2 object CLI transfers up to 50 MB, including interruption and explicit recovery

Generic S3 uses the same low-level SigV4 foundation and has local adapter coverage, but external compatibility acceptance is still pending. The final release must either complete that smoke test or explicitly narrow the stable compatibility claim before tagging.

## Installation and deployment

This release does not provision production infrastructure automatically. Follow the [Cloudflare operations runbook](../operations/cloudflare.md) to create an isolated environment, configure secrets, apply D1 migrations in order, verify readiness, and deploy the Worker.

For an existing environment:

1. Back up valuable D1 data outside the repository.
2. Verify the target Cloudflare account, environment, D1 database, and current migration history.
3. Apply migrations `0001` through `0006` in order without modifying published files.
4. Keep `CREDENTIAL_MASTER_KEY` and `CREDENTIAL_MASTER_KEY_ID` unchanged for existing encrypted credentials.
5. Deploy separately, check `/api/v1/health`, and then run only the explicitly authorized provider smoke tests.

Remote migrations and deployment remain separate, owner-authorized operations. Installing source code or checking out the tag does not run either action.

## Known limitations

- Generic S3 has not yet passed an external-provider smoke test.
- No production environment, automated deployment, or one-click deployment path is included.
- The SDK and CLIs remain workspace-private and are not published npm packages.
- Multipart resumable uploads, automatic replication and repair, a full S3 gateway, multi-user tenancy, billing, quotas, and fine-grained RBAC are not included.
- The project has not completed an independent security audit and should not be used for critical or irreplaceable data without an operator risk review and recovery plan.
